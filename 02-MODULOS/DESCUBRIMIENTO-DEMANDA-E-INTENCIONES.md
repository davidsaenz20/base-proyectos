# MÓDULO UNIVERSAL DE DESCUBRIMIENTO DE DEMANDA E INTENCIONES

## PROPÓSITO

Definir un procedimiento universal para descubrir, investigar, interpretar y estructurar la demanda existente alrededor de un proyecto cuando las URLs, temas, contenidos o páginas que deben crearse no están completamente predeterminados.

Este módulo es independiente del modelo de negocio.

Puede utilizarse para:

- webs de afiliación;
- webs de contenido;
- webs informativas;
- webs de servicios;
- directorios;
- comparadores;
- marketplaces;
- e-commerce;
- generación de leads;
- proyectos locales;
- proyectos nacionales;
- proyectos internacionales;
- otros modelos de negocio en los que sea necesario descubrir qué busca realmente el mercado.

El objetivo no es generar el mayor número posible de keywords.

El objetivo es descubrir oportunidades reales de demanda y determinar qué problemas, necesidades, preguntas, objetivos o intenciones justifican la creación de una página, contenido, servicio, categoría, producto u otra unidad dentro del proyecto.

---

# 1. PRINCIPIO FUNDAMENTAL

KEYWORD ≠ INTENCIÓN ≠ URL

Una keyword es una expresión utilizada por una persona para buscar algo.

Una intención representa lo que esa persona realmente quiere conseguir con esa búsqueda.

Una URL representa una respuesta o solución concreta que el proyecto decide ofrecer.

Por tanto, el sistema nunca debe convertir automáticamente cada keyword descubierta en una URL.

Proceso obligatorio:

KEYWORDS
↓
INTERPRETACIÓN
↓
INTENCIÓN
↓
AGRUPACIÓN
↓
OPORTUNIDAD
↓
DECISIÓN DE URL

---

# 2. CUÁNDO UTILIZAR ESTE MÓDULO

Este módulo debe activarse cuando:

- no exista una matriz de URLs previamente definida;
- no se conozca de antemano toda la demanda existente;
- el proyecto dependa de búsquedas orgánicas;
- sea necesario descubrir nuevos problemas o necesidades;
- exista incertidumbre sobre qué contenidos crear;
- exista incertidumbre sobre qué categorías crear;
- exista incertidumbre sobre qué servicios deberían tener páginas independientes;
- sea necesario determinar si varias keywords representan una misma intención;
- sea necesario ampliar una web de forma basada en demanda real.

No debe utilizarse obligatoriamente cuando la estructura de URLs esté completamente determinada por una lógica externa.

Ejemplo:

SERVICIO + LOCALIDAD

Si el sistema ya ha definido de forma justificada todas las combinaciones válidas, puede utilizarse una matriz de URLs sin necesidad de descubrir cada URL mediante keyword research.

Sin embargo, este módulo puede utilizarse posteriormente para validar, priorizar y ampliar dicha estructura.

---

# 3. OBJETIVO DEL PROCESO

El proceso debe responder como mínimo a estas preguntas:

1. ¿Qué está buscando el mercado?
2. ¿Qué problemas intenta resolver?
3. ¿Qué objetivos intenta conseguir?
4. ¿Qué preguntas realiza?
5. ¿Qué necesidades comerciales existen?
6. ¿Qué intenciones son diferentes?
7. ¿Qué keywords representan cada intención?
8. ¿Qué intenciones merecen una página independiente?
9. ¿Cuáles deben agruparse?
10. ¿Cuáles deben descartarse?
11. ¿Qué prioridad tiene cada oportunidad?
12. ¿Qué tipo de página debería responder a cada intención?

Las fuentes pueden incluir:

- resultados de búsqueda de Google;
- sugerencias de Google;
- búsquedas relacionadas;
- People Also Ask;
- herramientas profesionales de keyword research;
- datos de terceros;
- marketplaces;
- foros;
- Reddit;
- comunidades;
- redes sociales;
- preguntas frecuentes;
- comentarios de usuarios;
- reviews;
- páginas de competidores;
- catálogos;
- datos internos del propio proyecto;
- consultas realizadas por usuarios;
- datos de conversión;
- otras fuentes relevantes.

La IA puede utilizar información cualitativa para descubrir necesidades que no aparezcan claramente en una herramienta de keywords.

---

# 5. NO INVENTAR DATOS

La IA nunca debe presentar como dato real:

- volumen de búsqueda;
- dificultad;
- CPC;
- competencia;
- tendencias;
- número de búsquedas;
- conversiones;
- tráfico;
- porcentajes;
- cualquier otra métrica cuantitativa;

si no dispone de una fuente que proporcione ese dato.

Cuando un dato no esté disponible debe indicarse claramente:

- desconocido;
- no disponible;
- estimación;
- hipótesis;
- requiere comprobación.

Las estimaciones nunca deben presentarse como datos reales.

---

# 6. MODO DE INVESTIGACIÓN

El sistema debe poder trabajar en dos modos.

## MODO A — INVESTIGACIÓN CON DATOS DISPONIBLES

Cuando el sistema tenga acceso a fuentes de datos, debe realizar la investigación directamente.

Debe:

1. descubrir términos;
2. recopilar datos;
3. normalizar los datos;
4. eliminar duplicados;
5. interpretar las intenciones;
6. agrupar;
7. priorizar;
8. proponer URLs.

---

## MODO B — INVESTIGACIÓN ASISTIDA POR EL USUARIO

Cuando el sistema no tenga acceso directo a una fuente necesaria, debe solicitar al usuario los datos concretos que necesita.

Ejemplo:

"Necesito datos de Google Keyword Planner para estas categorías. Exporta el resultado y tráelo al proyecto."

El sistema debe especificar:

- qué herramienta utilizar;
- qué términos introducir;
- qué país seleccionar;
- qué idioma seleccionar;
- qué periodo utilizar;
- qué columnas exportar;
- qué formato entregar.

Una vez recibidos los datos, el sistema continúa el proceso.

# 8. FAMILIAS DE INTENCIÓN

El sistema debe intentar identificar diferentes tipos de intención.

No debe limitarse exclusivamente a las clasificaciones tradicionales de:

- informacional;
- navegacional;
- comercial;
- transaccional.

También debe detectar intenciones específicas del proyecto.

Ejemplos:

## INFORMACIÓN

"cómo hacer..."

"qué es..."

"por qué..."

## NECESIDAD

"qué necesito para..."

"qué hace falta para..."

"qué necesito comprar para..."

## COMPARACIÓN

"X vs Y"

"mejor X"

"alternativas a X"

## DECISIÓN

"qué X elegir"

"qué X comprar"

"cuál es mejor para..."

## EJECUCIÓN

"cómo montar..."

"cómo preparar..."

"cómo instalar..."

## SOLUCIÓN

"solución para..."

"cómo solucionar..."

## LOCAL

"X en Madrid"

"X cerca de mí"

## TRANSACCIONAL

"comprar X"

"precio X"

"X barato"

Estas categorías son orientativas.

El sistema debe crear categorías adicionales cuando el proyecto lo requiera.

---

# 9. DESCUBRIMIENTO DE INTENCIONES OCULTAS

El sistema no debe depender únicamente de keywords explícitas.

Debe buscar también necesidades implícitas.

Ejemplo:

Keyword:

"huerto balcón pequeño"

Posibles intenciones:

- saber qué se puede cultivar;
- saber qué materiales comprar;
- saber cómo organizar el espacio;
- encontrar un kit;
- conocer plantas adecuadas;
- evitar errores;
- calcular presupuesto.

Una única keyword puede contener varias necesidades.

El sistema debe investigar si esas necesidades:

A. pertenecen a una misma solución;

B. deben formar parte de una misma página;

C. justifican páginas independientes.

---

# 10. AGRUPACIÓN DE KEYWORDS

Las keywords deben agruparse por intención, no solamente por similitud textual.

Ejemplo:

"huerto en balcón"

"huerto balcón pequeño"

"montar huerto en balcón"

"huerto para principiantes en balcón"

pueden representar una única intención.

Pero:

"qué plantar en un balcón"

"cómo regar un huerto de balcón"

"mejores plantas para balcón con sombra"

pueden representar necesidades diferentes.

La decisión debe basarse en:

- objetivo del usuario;
- necesidad;
- solución esperada;
- resultados de búsqueda;
- contenido necesario para responder;
- posibilidad de satisfacer varias consultas con una única página.

---

# 11. VALIDACIÓN MEDIANTE SERP

Cuando sea posible, el sistema debe analizar los resultados reales de búsqueda.

Debe comprobar:

- qué tipo de páginas aparecen;
- qué temas cubren;
- qué necesidades responden;
- qué formato utilizan;
- si las keywords comparten resultados;
- si Google parece considerar las consultas equivalentes;
- si existen resultados comerciales;
- si existen resultados informativos;
- si existen resultados locales;
- si existe intención transaccional;
- si existe oportunidad para una solución diferente.

La SERP debe utilizarse como evidencia adicional para determinar si dos keywords representan la misma intención.

---

# 12. DECISIÓN DE UNA URL

Una intención puede justificar una URL independiente cuando:

- existe una necesidad claramente diferenciada;
- el usuario espera una respuesta diferente;
- la solución requiere contenido diferente;
- la página puede aportar valor propio;
- no es simplemente una variante artificial de otra URL;
- existe una razón lógica para que el usuario llegue directamente a ella.

No debe crearse una URL independiente únicamente porque:

- existe una keyword;
- existe una pequeña variación ortográfica;
- cambia el orden de las palabras;
- cambia ligeramente una preposición;
- cambia un sinónimo;
- la keyword tiene volumen.

---

# 13. CONSOLIDACIÓN

Antes de aprobar nuevas URLs, el sistema debe intentar reducir duplicidades.

Para cada posible URL debe preguntar:

"¿Esta página resuelve una necesidad diferente o puedo resolverla correctamente dentro de otra página?"

Si puede resolverse correctamente dentro de otra página:

NO CREAR NUEVA URL.

Si necesita una solución diferenciada:

CREAR / PROPONER NUEVA URL.

---

# 14. CANIBALIZACIÓN

El sistema debe detectar posibles conflictos entre URLs.

Debe identificar:

- intenciones prácticamente idénticas;
- páginas que podrían competir por la misma búsqueda;
- variaciones artificiales;
- páginas demasiado similares;
- páginas que deberían consolidarse;
- páginas que deberían diferenciarse mejor.

La solución puede ser:

- fusionar;
- eliminar;
- redirigir;
- modificar intención;
- diferenciar contenido;
- mantener ambas si existe una justificación clara.

---

# 15. TIPOS DE OPORTUNIDAD

Cada intención detectada debe poder clasificarse como:

🟢 OPORTUNIDAD CLARA

Existe una necesidad diferenciada y una razón sólida para crear una página.

🟡 OPORTUNIDAD POTENCIAL

Existe una necesidad interesante pero requiere más investigación.

🟠 OPORTUNIDAD CONDICIONAL

Puede tener sentido dependiendo del modelo de negocio, monetización o datos adicionales.

🔴 DESCARTADA

No existe suficiente razón para crear una página independiente.

---

# 16. PRIORIZACIÓN

Las oportunidades deben priorizarse mediante múltiples factores.

Como mínimo:

- demanda;
- relevancia;
- intención comercial;
- valor para el usuario;
- potencial de monetización;
- competencia;
- dificultad;
- capacidad de aportar valor;
- coste de creación;
- coste de mantenimiento;
- posibilidad de automatización;
- relación con otras páginas;
- potencial de expansión.

No debe utilizarse una única métrica para decidir.

↓

# 21. SEARCH CONSOLE COMO FUENTE PROPIA

Debe utilizarse para descubrir:

- nuevas intenciones;
- keywords para las que ya aparece el proyecto;
- páginas que reciben impresiones;
- oportunidades de expansión;

El sistema debe poder incorporar estas consultas al proceso de descubrimiento.

# 24. REGLA CONTRA LA CREACIÓN MASIVA SIN VALOR

El sistema nunca debe utilizar el keyword research como excusa para crear automáticamente miles de páginas.

La existencia de una keyword no constituye por sí misma una razón suficiente para crear una URL.

Antes de aprobar una URL debe existir:

- intención identificada;
- necesidad diferenciada;
- solución posible;
- valor que pueda aportar el proyecto;
- justificación de la página.

Si estos elementos no existen:

NO CREAR.

---

# 25. RELACIÓN CON LA AUTOMATIZACIÓN

El descubrimiento puede automatizarse parcialmente.

La automatización puede encargarse de:

- recopilar datos;
- normalizar keywords;
- eliminar duplicados;
- clasificar términos;
- detectar patrones;
- agrupar candidatos;
- calcular puntuaciones;
- detectar cambios;
- generar propuestas;
- preparar informes.

Pero las decisiones de alto impacto deben poder ser revisadas.

Especialmente:

- creación de nuevas URLs;
- eliminación de URLs;
- consolidación;
- definición de intención;
- priorización estratégica;
- publicación masiva.

28. CRITERIO DE ÉXITO

El objetivo del módulo no es:

"encontrar muchas keywords."

El objetivo es:

"encontrar oportunidades reales que permitan construir páginas capaces de resolver necesidades concretas."

Por tanto, el éxito debe medirse mediante:

oportunidades descubiertas;

oportunidades válidas;

porcentaje de oportunidades descartadas;

páginas creadas;

tráfico;

impresiones;

clics;

conversiones;

ingresos;

utilidad para el usuario;

coste de creación;

coste de mantenimiento;

rendimiento por intención.



---

29. PRINCIPIO DE APRENDIZAJE

El sistema debe utilizar los resultados reales para mejorar futuras decisiones.

Si una determinada clase de intención:

genera tráfico;

genera conversiones;

genera ingresos;

recibe interacción;

tiene bajo coste de creación;


debe aumentar su prioridad.

Si otra:

no recibe impresiones;

no recibe clics;

no genera conversiones;

tiene alto coste;

aporta poco valor;


debe reducirse o descartarse.


---

30. SALIDA DEL MÓDULO

El módulo debe terminar entregando una estructura que pueda consumir el resto del sistema.

Como mínimo:

PROYECTO ↓ DEMANDA DESCUBIERTA ↓ INTENCIONES ↓ CLUSTERS ↓ OPORTUNIDADES ↓ PRIORIDADES ↓ TIPO DE PÁGINA ↓ ARQUITECTURA ↓ URLs

A partir de este punto, el módulo correspondiente al tipo de proyecto debe encargarse de construir la solución.


---

31. PRINCIPIO FINAL

La función de este módulo no es crear contenido.

No es crear páginas.

No es buscar únicamente keywords.

No es hacer SEO por sí mismo.

Su función es descubrir y estructurar la demanda para que el sistema pueda decidir:

QUÉ NECESITA EL MERCADO ↓ QUÉ INTENCIONES EXISTEN ↓ QUÉ INTENCIONES SON DIFERENTES ↓ QUÉ OPORTUNIDADES MERECEN ATENCIÓN ↓ QUÉ PÁGINAS TIENE SENTIDO CREAR ↓ QUÉ SOLUCIÓN DEBE OFRECER CADA UNA

La ventaja buscada es que cualquier tipo de proyecto pueda partir de demanda real y no de una estructura de URLs arbitraria.

El sistema debe preferir:

POCAS PÁGINAS ÚTILES

antes que

MUCHAS PÁGINAS SIN VALOR.

Y debe preferir:

INTENCIONES REALES

antes que

KEYWORDS AISLADAS.
