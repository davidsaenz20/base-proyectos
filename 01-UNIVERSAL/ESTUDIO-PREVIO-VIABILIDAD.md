# ESTUDIO PREVIO DE VIABILIDAD

## PROPÓSITO

Establecer un estudio previo y exhaustivo que debe realizarse cuando un proyecto implique crear un producto, servicio, negocio, plataforma, aplicación, web, automatización, sistema de IA, SaaS, API o cualquier solución que requiera una inversión relevante de tiempo, dinero o recursos.

El objetivo es determinar:

- si existe un problema o necesidad real;
- si existe una oportunidad;
- si existe demanda suficiente;
- qué alternativas y competidores existen;
- si existe una diferenciación defendible;
- cómo podría monetizarse;
- qué costes y riesgos existen;
- si técnicamente puede construirse;
- si económicamente puede sostenerse;
- y, especialmente, si existen alternativas capaces de hacer viable una idea que inicialmente parezca débil.

Este estudio debe realizarse ANTES de comprometerse con la construcción técnica completa cuando la naturaleza del proyecto lo requiera.

---

## PRINCIPIO FUNDAMENTAL

La IA debe analizar e informar.

La IA puede recomendar:

- CONTINUAR;
- PIVOTAR;
- REPLANTEAR;
- NO CONTINUAR.

Pero la IA NO decide unilateralmente el destino del proyecto.

La decisión final corresponde siempre al usuario.

### REGLA

Una recomendación negativa del sistema NO significa que el proyecto quede automáticamente cancelado.

Si el usuario decide continuar, el sistema debe respetar la decisión, registrar la decisión y continuar aplicando la metodología.

---

# 1. CUÁNDO DEBE REALIZARSE

El estudio previo debe utilizarse especialmente cuando:

- se propone una nueva idea de negocio;
- se pretende crear un producto nuevo;
- se pretende crear una web con finalidad comercial;
- se pretende crear una aplicación;
- se pretende crear un SaaS;
- se pretende crear una plataforma;
- se pretende crear una automatización comercial;
- se pretende crear un servicio basado en IA;
- exista una inversión relevante;
- exista incertidumbre importante sobre demanda o monetización;
- una decisión incorrecta pueda provocar un desperdicio significativo de recursos.

No debe convertirse en burocracia innecesaria para tareas simples, mantenimiento, pequeñas correcciones o trabajos cuyo objetivo ya esté suficientemente validado.

---

# 2. OBJETIVO DEL ESTUDIO

El estudio debe responder como mínimo:

1. ¿Qué problema se intenta resolver?
2. ¿Quién tiene ese problema?
3. ¿Con qué frecuencia aparece?
4. ¿Cómo lo resuelve actualmente?
5. ¿Qué alternativas existen?
6. ¿Quiénes son los competidores?
7. ¿Existe demanda?
8. ¿Existe mercado suficiente?
9. ¿Qué diferencia tendría nuestra solución?
10. ¿Por qué alguien la utilizaría?
11. ¿Quién pagaría?
12. ¿Cuánto podría pagar?
13. ¿Cuánto costaría adquirir usuarios?
14. ¿Cuánto costaría operar el sistema?
15. ¿Qué dificultad técnica existe?
16. ¿Qué riesgos existen?
17. ¿Puede escalar?
18. ¿Qué MVP permitiría probarlo con menor coste?
19. ¿Qué cambios podrían aumentar la viabilidad?
20. ¿Cuál es la recomendación final?

---

# 3. ESTUDIO EXHAUSTIVO

La IA debe investigar, cuando sea necesario:

## 3.1 PROBLEMA

Analizar:

- problema principal;
- problemas secundarios;
- frecuencia;
- gravedad;
- urgencia;
- coste del problema;
- soluciones actuales;
- frustraciones existentes.

Debe evitarse asumir que un problema existe simplemente porque la idea parece interesante.

---

## 3.2 USUARIO

Determinar:

- usuario principal;
- usuarios secundarios;
- necesidades;
- comportamiento;
- contexto;
- capacidad de pago;
- motivaciones;
- objeciones;
- canales utilizados.

---

## 3.3 DEMANDA

Buscar señales reales de demanda.

Cuando sea posible utilizar fuentes externas:

- búsquedas;
- tendencias;
- comunidades;
- foros;
- marketplaces;
- productos existentes;
- reseñas;
- anuncios;
- empresas que ya pagan por soluciones similares;
- estadísticas;
- estudios;
- datos públicos.

No debe confundirse interés teórico con demanda real.

---

## 3.4 MERCADO

Analizar:

- tamaño aproximado;
- mercado objetivo inicial;
- mercado accesible;
- crecimiento;
- tendencias;
- barreras;
- regulación;
- oportunidades geográficas;
- oportunidades sectoriales.

Cuando los datos exactos no existan, deben utilizarse estimaciones razonables y declarar claramente que son estimaciones.

---

## 3.5 COMPETENCIA

Buscar:

### Competencia directa

Soluciones que resuelvan prácticamente el mismo problema.

### Competencia indirecta

Soluciones diferentes que satisfagan la misma necesidad.

### Sustitutos

Formas manuales o gratuitas de resolver el problema.

No debe concluirse que una idea es buena porque "no existe exactamente igual".

La ausencia de competencia debe analizarse también como posible señal de falta de demanda.

---

# 4. SOLUCIONES ALTERNATIVAS

Esta sección es OBLIGATORIA.

Si la idea inicial parece poco viable, la IA debe intentar encontrar formas de mejorarla antes de recomendar abandonarla.

Debe estudiar, cuando corresponda:

- cambio de público;
- cambio de nicho;
- cambio de problema;
- cambio de posicionamiento;
- cambio de propuesta de valor;
- modelo B2B;
- modelo B2C;
- modelo B2B2C;
- suscripción;
- pago por uso;
- pago por resultado;
- generación de leads;
- afiliación;
- marketplace;
- comisión;
- publicidad;
- licencias;
- servicio profesional;
- producto digital;
- automatización;
- integración con plataformas existentes;
- reducción del alcance;
- MVP más sencillo;
- producto complementario;
- pivot parcial;
- pivot completo.

### REGLA

No debe abandonarse una idea únicamente porque la primera formulación sea débil.

Primero deben buscarse alternativas razonables que puedan mejorar su viabilidad.

---

# 5. MVP ALTERNATIVOS

Cuando exista incertidumbre, deben proponerse diferentes formas de comprobar la idea.

Ejemplo:

### MVP A
Solución completa.

### MVP B
Versión manual parcialmente automatizada.

### MVP C
Landing + formulario + intervención manual.

### MVP D
Prototipo sin infraestructura definitiva.

### MVP E
Prueba limitada a un nicho concreto.

El objetivo es descubrir cuál permite obtener evidencia real con menor coste y riesgo.

---

# 6. VIABILIDAD TÉCNICA

Analizar:

- tecnologías necesarias;
- APIs;
- dependencias;
- integraciones;
- infraestructura;
- seguridad;
- mantenimiento;
- escalabilidad;
- costes técnicos;
- limitaciones de terceros.

La viabilidad técnica no debe confundirse con la viabilidad empresarial.

---

# 7. VIABILIDAD ECONÓMICA

Analizar cuando corresponda:

- costes iniciales;
- costes mensuales;
- coste por usuario;
- coste por operación;
- coste de IA;
- adquisición de clientes;
- ingresos potenciales;
- margen;
- punto de equilibrio;
- escalabilidad económica.

Las cifras deben diferenciar:

- dato comprobado;
- estimación;
- hipótesis.

---

# 8. RIESGOS

Identificar:

- demanda insuficiente;
- competencia;
- dependencia de terceros;
- costes elevados;
- dificultad técnica;
- regulación;
- seguridad;
- privacidad;
- adquisición de usuarios;
- monetización;
- escalabilidad;
- ejecución.

Cada riesgo importante debe tener, cuando sea posible:

- impacto;
- probabilidad;
- mitigación.

---

# 9. MATRIZ DE VIABILIDAD

La IA debe realizar una valoración estructurada.

Como mínimo:

- problema;
- usuario;
- demanda;
- mercado;
- competencia;
- diferenciación;
- monetización;
- costes;
- viabilidad técnica;
- escalabilidad;
- riesgos.

Cada dimensión puede valorarse de 0 a 10.

Debe explicarse brevemente cada valoración.

La puntuación global NO debe presentarse como una verdad matemática.

Es una herramienta de decisión.

---

# 10. RECOMENDACIÓN

El resultado debe clasificarse como:

## 🟢 CONTINUAR

Existe una oportunidad razonable y puede justificarse avanzar.

## 🟠 PIVOTAR

La idea original presenta problemas importantes, pero existe una alternativa con mejores posibilidades.

## 🟡 VALIDAR MÁS

La información disponible todavía no permite tomar una decisión suficientemente sólida.

## 🔴 NO RECOMENDADO

La evidencia disponible indica que continuar presenta una relación riesgo/beneficio desfavorable.

---

# 11. DECISIÓN DEL USUARIO

Después del informe, la IA debe presentar claramente:

- conclusión;
- evidencias principales;
- riesgos;
- alternativas;
- recomendación;
- nivel de confianza;
- información que todavía falta.

Después debe quedar registrada la decisión del usuario.

Las posibilidades son:

- continuar;
- continuar con cambios;
- pivotar;
- investigar más;
- detener.

### REGLA FUNDAMENTAL

La recomendación pertenece al sistema.

La decisión pertenece al usuario.

La IA nunca debe interpretar automáticamente una recomendación como una orden de cancelar el proyecto.

---

# 12. SI EL USUARIO DECIDE CONTINUAR

El sistema debe:

1. registrar la decisión;
2. identificar qué hipótesis deben validarse;
3. actualizar la definición;
4. actualizar el roadmap;
5. incorporar los riesgos;
6. continuar con la metodología universal;
7. realizar ANALYZE cuando corresponda.

---

# 13. SI EL USUARIO DECIDE PIVOTAR

El sistema debe:

1. registrar la decisión;
2. identificar qué elementos se conservan;
3. identificar qué elementos cambian;
4. repetir el estudio sobre la nueva propuesta cuando el cambio sea significativo;
5. actualizar documentación;
6. actualizar roadmap;
7. continuar únicamente cuando la nueva definición esté validada.

---

# 14. SI EL USUARIO DECIDE DETENER

El sistema debe:

1. registrar la decisión;
2. conservar el estudio;
3. registrar los motivos;
4. registrar posibles oportunidades futuras;
5. dejar el proyecto correctamente cerrado.

Detener un proyecto después de descubrir que no es viable se considera una ejecución correcta de la metodología.

---

# 15. EVIDENCIA Y FUENTES

Cuando se utilicen fuentes externas, registrar:

- fuente;
- fecha;
- dato obtenido;
- interpretación;
- impacto sobre la decisión.

Las afirmaciones importantes deben poder rastrearse hasta una fuente o identificarse expresamente como hipótesis.

---

# 16. REGLA DE NO CONSTRUCCIÓN PREMATURA

Cuando el estudio previo sea obligatorio, la IA no debe iniciar una construcción técnica significativa antes de completar:

- estudio;
- alternativas;
- evaluación;
- recomendación;
- decisión del usuario.

Puede realizarse una prueba técnica mínima si dicha prueba es necesaria para determinar la propia viabilidad.

---

# 17. PRINCIPIO DE MÍNIMO RIESGO

Antes de construir una solución grande, la IA debe intentar identificar una forma más barata, rápida o sencilla de comprobar las hipótesis críticas.

La pregunta prioritaria será:

> ¿Cuál es la prueba más pequeña que puede demostrar si esta idea merece ser construida?

---

# 18. RELACIÓN CON LA METODOLOGÍA UNIVERSAL

Este estudio no sustituye:

- CLARIFY;
- ANALYZE;
- definición;
- requisitos;
- arquitectura;
- planificación;
- construcción;
- pruebas;
- validación;
- CONVERGE.

Se incorpora como mecanismo previo de decisión cuando el proyecto lo requiera.

La metodología debe impedir tanto:

- construir sin haber comprobado si merece la pena;

como:

- realizar estudios innecesarios en proyectos simples ya validados.

---

# 19. RESULTADO FINAL

El estudio previo debe producir una conclusión comprensible:

### PROPUESTA

Qué se quiere construir.

### OPORTUNIDAD

Qué problema y mercado existen.

### EVIDENCIA

Qué datos respaldan o contradicen la idea.

### ALTERNATIVAS

Qué otras formulaciones pueden ser más viables.

### MVP RECOMENDADO

Cuál es la forma más sencilla de probarla.

### VIABILIDAD

Valoración estructurada.

### RECOMENDACIÓN

Continuar / pivotar / validar más / no recomendado.

### DECISIÓN

Decisión final tomada por el usuario.

La metodología solo podrá pasar a construcción cuando exista una decisión explícita de continuar.
